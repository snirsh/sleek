# Big-PR Plan — UX + Performance for 5m+ reviews

> Target case: a large benchmark PR (~430 changed regions) (current: ~6–7 min end-to-end after the region-index
> skeleton work). Two goals: (1) the wait *feels* alive and useful from second one;
> (2) the wall clock itself drops by cutting what the LLM reads and parallelizing smarter.
>
> Grounding: `ingest.ts:219` (gh-based ingest, no filtering), `scaffolder.ts:403` (3a/3b),
> `scaffoldjob.ts:19-25` (NDJSON event log), `processui.ts:51-197` (client state machine),
> `risk.ts:16` (UI-only risk). Today there is **no** file filtering, **no** dedup, **no**
> graph/risk logic, **no** stacked-PR awareness, and the frontend shows only coarse stage
> labels ("Skeleton: laid down 4 layers", "Detail: 2 of 4").

## Success metrics

- **Time-to-first-readable-content** (skeleton layers visible in the UI): < 90s on the benchmark PR.
- **End-to-end** on the benchmark PR: ≤ 3–4 min (from 6–7).
- **Perceived progress**: never more than ~10s without a new visible event while running.

## Workstream A — UX: make the run visible (no scaffolder changes needed)

The event plumbing already exists (`ScaffoldJob` seq'd NDJSON + reattach). These waves
widen what's emitted and what's rendered.

### A1. Richer event vocabulary
Extend `ScaffoldProgressEvent` / `LoggedEvent` (scaffoldjob.ts:19):
- `stage:"ingest"` gains `files`, `regions`, `bytes` counts.
- New `stage:"plan"` event carrying the **skeleton's layer plan** the moment 3a returns:
  `{layers: [{id, title, regionCount, files[]}]}` — before any detail worker starts.
- Per-layer detail lifecycle: `{stage:"detail", layer, status:"start"|"done"|"retry", ms}`
  instead of only an aggregate `done/total` counter.
- `stage:"activity"` — throttled (≤1/2s) one-line summaries of CLI runner activity
  (tool-use lines from the Claude Code / Codex stream-json output the cli-runner already
  parses), so the user sees *what* the agent is reading, not just that it's alive.
- Skeleton fan-out visibility: when the >8-files/>25-regions fan-out fires
  (scaffolder.ts:301-329), emit subagent spawn/finish events.

### A2. Progress UI: overall bar → per-agent breakdown
- **Overall bar** with weighted phases (ingest ~5%, context ~10%, skeleton ~30%,
  detail ~55%) — weights calibrated from stored timings (A3).
- On the `plan` event, the bar **breaks down into one row per layer** (detail worker):
  layer title, region count, spinner → checkmark → findings count. Same idiom as
  nx `run-many` / GitHub Actions matrix rows / Claude Code's workflow tree.
- Activity ticker under the bar showing the latest `activity` line per running worker.
- Keep everything in the existing quiet IDE aesthetic (no chips/pills — see UI-taste
  memory); rows are the Zed-style flat list, not cards.

### A3. Progressive hydration — *the* big perceived-latency win
- When 3a lands, **render the review immediately**: file tree + diff + skeleton layers
  (titles, anchors), each layer showing a subtle "analyzing…" shimmer where findings
  will appear. Detail results stream in per layer and hydrate in place.
- Requires: persist/serve a partial scaffold (layers without bundles/findings) and a
  `PATCH`-style per-layer completion event on the stream. Staleness key stays PR+headSha.
- The user starts reading low-risk files ~60–90s in instead of staring at a spinner
  for 6 minutes.

### A4. ETA + history
- Store per-run phase timings in SQLite keyed by size bucket (files/regions/LOC);
  show "~4 min remaining, based on similar PRs". Falls back to weights when cold.

### Borrowed ideas worth folding in
- **Docker-pull-style per-layer bars** (parallel rows with independent completion) — A2.
- **Vercel/Turbo collapsible log groups** per phase for the activity feed — A1/A2.
- **Skeleton screens** (Slack/Linear-style shimmer) instead of spinners in the diff
  panel — A3.
- **tqdm-style rate + ETA** on the overall bar — A4.
- **Cancel affordance per run stays** (already exists via /api/scaffold/cancel); add a
  "review what's done so far" option on cancel once A3 exists (partial scaffold is real).

## Workstream B — Performance: shrink and shard the work

### B1. Deterministic noise stripping (biggest free win — do first)
New pre-context pass in ingest (`src/ingest/noise.ts`), purely mechanical:
- **Classifier**, in priority order:
  1. `.gitattributes` `linguist-generated` / `linguist-vendored` (respect the repo's
     own declaration; `git check-attr` in the worktree).
  2. Generated-header markers in file head (`@generated`, `Code generated by`, `DO NOT
     EDIT`).
  3. Path heuristics: `pnpm-lock.yaml`, `yarn.lock`, `package-lock.json`, `Cargo.lock`,
     `go.sum`, `*.min.*`, `dist/`, `build/`, `__snapshots__/`, `*.snap`, `*.pb.*`,
     `*.generated.*`, vendored dirs.
  4. Size heuristic: single file > N KB of diff with near-zero comment/blank variety.
- **Collapse, don't drop**: classified files become one synthetic "noise" region per
  file with a one-line note — e.g. *"pnpm-lock.yaml changed (+1.2K/−800 lines) —
  present and consistent with package.json edits; contents not reviewed."* The skeleton
  prompt keeps existence/consistency signal (so "deps changed but lockfile didn't"
  false-negatives can't happen) while the diff body never reaches the model.
- Tiling stays valid: noise regions belong to a synthetic `__noise__` layer rendered
  collapsed in the UI with a "show anyway" escape hatch.
- Expect this alone to remove the majority of line count on lockfile-heavy PRs.

### B2. Hunk dedup by normalized hash
After region parsing (`diff.ts`), before context building:
- Normalize each hunk (strip whitespace; optionally alpha-rename identifiers per
  language via the existing tree-sitter dependency) and hash.
- Groups with ≥K identical hashes → keep **one representative region**, replace the
  rest with a machine note: *"same edit applied in 37 other files (list)"*. Exact
  hashing, not embeddings — a deviating hunk hashes differently and stays in review.
- Representative's findings are echoed onto siblings in the UI (anchored per file).

### B3. Graph-aware grouping (nx / turbo skill)
- Detect monorepo tooling in the target worktree: `nx.json` → `nx graph --file=…`;
  `turbo.json` → `turbo query` / `--dry=json`. Build a file→project map + project
  dependency edges. Package as a **skill/helper the CLI scaffolder providers load**
  (mirrors how the fan-out paragraph is injected at scaffolder.ts:309).
- Feed the skeleton prompt **pre-clusters as hints**: "these regions share a project /
  producer-consumer edge / test-of relationship" — the model still owns layer
  boundaries, but the graph puts a changed producer with its consumers and tests
  instead of relying on path similarity.
- Fallback when no graph tool: current behavior (directory grouping) unchanged.

### B4. Risk score + tiered depth + balanced shards
Cheap per-file scoring computed locally (extends `risk.ts` from UI-only to pipeline):
- Inputs: churn (git log count), graph centrality (from B3 map or tree-sitter
  neighbors), runtime-vs-test/doc path, touches exported/public surface, has covering
  tests in the changeset.
- Uses:
  1. **Shard balancing**: detail fan-out shards by *estimated effort* (region LOC ×
     risk), capped per shard, instead of whatever layer sizes the skeleton produced —
     split oversized layers into sub-shards so no shard is the long pole.
  2. **Model tiering**: low-risk shards run on a cheap model (Sonnet via CLI
     `--model`, or Codex), the load-bearing core stays on opus-4-8/fable. Wire through
     the existing per-runner model plumbing (`llm.ts:75`, runner opts).
  3. Risk feeds the UI's initial-expand logic (already half-exists in risk.ts).

### B5. Two-pass depth + adversarial verification
- **Pass 1 (breadth, cheap model)**: current skeleton + a *light* detail sweep that
  outputs risk flags per layer, not full findings.
- **Pass 2 (depth, strong model)**: full detail only on layers pass 1 flagged high;
  low-risk layers keep the light pass's summary as their bundle.
- **Refuter**: before surfacing, every `critical`/`major` finding gets one independent
  cheap-model call prompted to refute it with the file content; refuted findings are
  demoted/annotated. Cross-shard aggregation dedups near-identical findings
  (normalized-text hash, reusing B2 machinery).
- Gate behind PR size (only fires above the fan-out thresholds) so small PRs keep the
  current single-pass latency.

### B6. Stacked-PR-exact diffs
- Ingest already takes GitHub's `baseRefOid`, but `gh pr diff` can include drift when
  the base branch has moved. Fix: in the local worktree compute
  `git merge-base <headSha> <baseRefOid>` and diff **three-dot against the merge-base**
  ourselves; for stacked PRs (base branch ≠ default branch) this reviews exactly the
  PR's own commits, never PR-1's.
- Surface stack context in the UI header: "based on `pr-1-branch` (not main)".

## Sequencing (each wave independently shippable)

| Wave | Items | Why this order |
|------|-------|----------------|
| 1 | **B1** noise stripping + **B6** merge-base diff | Pure-deterministic, no prompt changes, biggest token cut, de-risks everything after |
| 2 | **A1 + A2** event vocabulary + progress rows | Plumbing exists; instant UX payoff while B-work continues |
| 3 | **A3** progressive hydration (+ A4 ETA) | Depends on A1's `plan` event; the headline perceived-latency fix |
| 4 | **B2** hunk dedup + **B4** risk score/tiering/balanced shards | B4 shard-split changes 3b fan-out; measure on the benchmark PR via the smoke harness |
| 5 | **B3** nx/turbo skill | Additive prompt hint; needs B4's map plumbing |
| 6 | **B5** two-pass + refuter | Most invasive; only worth it once 1–5 land and we re-measure |

Measure after every wave with the existing smoke harness against the benchmark PR (baseline
timings in memory): record end-to-end, time-to-skeleton, tokens/lines sent.
